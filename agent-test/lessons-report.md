# 从 roofline-inference 到推理引擎：启示、应用与实测收益

2026-10-06 · Qwen3-0.6B BF16 · MacBook Air M4 24 GB · 单流 GPU 推理

本次完成了一个可运行的推理原型，但**没有证明它稳定快于 mlx-lm**。主要结果是：减少 decode 投影调用后，端到端 decode 多数点仍接近基线；32k 上下文出现明显退化。Roofline 最有价值的启示是帮助判断收益上限，以及区分“少做了调度工作”和“减少了瓶颈资源消耗”。这次实现做到了前者，没有改变后者。

## 1. 从项目中得到的启示

### 1.1 Decode 的主要成本是流量，融合只能争取剩余的小部分

原项目给出的 Qwen3-0.6B BF16 权重流量约为每 token 1.19 GB，KV 读流量随上下文增长；在校准的 102.7 GB/s 带宽下，decode 时间下界约为：

```text
T_decode(ctx) ≈ 11.6 ms + ctx × 1.12 μs
```

上下文 512、4k、32k 对应约 12.2、16.2、48.2 ms。项目的历史 mlx-lm 测量已经达到约 90–95% 的 bound 效率。这意味着，在该校准条件下，A 级实现优化的剩余空间通常只是几个到十几个百分点，而不是数倍。这里的 bound 使用 burst 校准值，不能直接当作本次热状态下的严格性能天花板。

因此，我选择合并 Q/K/V 和 gate/up 投影，减少小算子的固定成本；没有引入量化、投机解码、KV 压缩，也没有把部分计算转到 CPU。项目的共享带宽实验已经表明，CPU 与 GPU 同时读不会增加总可达带宽。

这一选择也有明确的收益限制：拼接投影权重不会减少权重的总字节数，不会减少 attention 对 KV 的读取。主导资源保持不变。

### 1.2 Prefill 的优化目标应是实际矩阵形状与 attention 效率

原项目把 prefill 的损失分成两段：

- 短 prompt：小 GEMM 并行度不足、小算子和分块调度开销。
- 长 prompt：attention 计算与真实分块调用效率，以及持续负载下的热降频。

项目指出，带宽达到较高利用率所需的并发约为 1k 线程，而算力需要约 16k–32k 线程；短 prompt 的矩阵形状很难提供足够的并行工作。因此，简单套用方阵 GEMM 的峰值效率，不能预测 Qwen3 小矩阵的性能。

我据此尝试了 prefill 投影拼接、batched GEMM 和最后一个 prompt token 的调度合并。但这些尝试未通过本次采用的严格数值或生成序列检查，没有进入默认路径。本次没有重写或调优 attention kernel，也没有实现专用小 GEMM kernel，因而没有真正解决项目指出的主要 prefill 瓶颈。

### 1.3 Kernel 数量不是延迟，孤立代价不能直接相加

项目拟合的依赖 kernel 固定成本 `t₀` 约为 2.44 μs，同时发现 CPU 建图、编码和 GPU 工作可以重叠。mlx-lm 的异步流水线已经隐藏了相当一部分引擎开销。

这让我保留一步异步 lookahead，避免每个 token 都先同步再构造下一步。也让我对融合的预期更加保守：减少调用次数可以降低局部成本，但如果这些成本原本已被其他工作覆盖，端到端收益会更小。

### 1.4 热状态是实验变量，不是最后可以忽略的误差

原项目记录过同一 32k prefill 从较冷状态的 55.8 s 增加到连续负载后的 70.7 s，差约 27%。这个变化大于本次多数优化的预期收益。

因此，本次重新运行配对基线，使用 AB/BA 交错顺序、相同等待时间和逐次记录；没有用历史较冷时的基线作加速比分母。但这些措施没有锁定实际温度、频率和后台负载，因此不能声称所有物理实验条件完全相同。

以上启示来自仓库的 [结果报告](../docs/report.md) 与 [设计笔记](../docs/design-notes.md)，本次没有重新校准硬件带宽或算力。

## 2. 怎么把启示应用到实现中

| Roofline 指向的问题 | 实际改动 | 状态与限制 |
| --- | --- | --- |
| Decode 小算子的固定成本 | Q/K/V 三次 GEMV 合成一次，gate/up 两次合成一次 | 默认启用；保留 BF16 权重与 KV，主要 DRAM 流量不变 |
| 小算子与中间结果开销 | 自定义 Metal residual + RMSNorm 融合 | 55 个可融合位置；数值测试通过，消融未显示稳定收益，默认关闭 |
| Prefill 小 GEMM 并行度 | 拼接投影，以及保持单个矩阵 M/N/K 的 batched GEMM | 严格数值检查失败，撤回 |
| Prefill 尾块重复前向与同步 | 把最后一个 prompt token 并入最后一块 | 512-token 生成序列检查失败，默认关闭 |
| 引擎额外计算与同步 | Greedy 直接对 logits 取 argmax，保留异步 lookahead | 默认启用；不提供 logprobs，API 功能比基线更窄 |
| Prefill 的对象生命周期与 allocator 开销 | 只求值 KV，立即丢弃无用 hidden graph；不在每个块清空 allocator cache | 默认启用；图释放有回归测试，allocator 策略对长上下文的影响尚未分离 |

引擎实现自己的 transformer forward 与生成调度，复用 MLX 的矩阵乘、attention 等 GPU 算子，以及 mlx-lm 的加载器、RoPE 和 KVCache。它没有实现新的 GEMM 或 attention 后端。

### 投影融合的收益预期有多大？

每层原有七次投影矩阵乘：Q、K、V、O、gate、up、down。合并后为四次：QKV、O、gate_up、down。28 层合计从 196 次减少到 112 次，少了 **84 次矩阵乘调用，约 42.9%**。

这不是整个 decode 的 kernel 数减少 42.9%。一次矩阵乘可能涉及多个 GPU dispatch，切片和布局处理也可能引入成本，本次没有获取新引擎的完整 GPU trace。

如果粗略把每次减少的调用视为省掉一个依赖 kernel 的固定成本：

```text
84 × 2.44 μs ≈ 0.205 ms / token
```

以本次 4k 基线的约 17.47 ms/token 为参照，这一量级约为 1.2%。这只是利用项目代价模型得到的粗略估计；它没有计入重叠、布局变化和有效带宽变化，不能作为真实节省量。

另外，当前实现为兼容原 prefill 投影而保留原权重，额外物化了约 **587 MB** packed 权重，相当于原模型参数字节数的 **49.3%**。加载和 packing 时间不计入请求延迟。本次实现没有获得模型内存占用方面的优势。

## 3. 实验条件与正确性标准

固定条件为 Apple M4、Qwen3-0.6B、BF16 权重与 KV、batch=1、greedy、相同 prompt token、65 个生成 token、2048-token chunk，以及相同 GPU stream、KVCache 类型和一步 lookahead。默认路径的逐块分区也与 mlx-lm 相同：先处理 L−1 个 token，再处理最后一个 token。

每对在同一进程内使用共享权重。16 至 4k 每个长度六对，16k 与 32k 每个长度两对，共 34 对；各长度先分别预热，随后交错 AB/BA。每次计时前同步 GPU、清空 allocator cache、等待 2 s。较长的场景只有两对，证据强度低于主实验。

基线是 mlx-lm 0.32.0 的 `generate_step`，MLX 为 0.32.3。计时包含 token ID 生成，不包含加载、packing、detokenizer 或终端输出；基线仍计算 logprobs，而新引擎不计算。因此结果适用于 token-only greedy 场景，不代表两个 API 的完整功能等价。

所有 34 对的生成 token 序列一致；固定分块的 12 组全位置 logits 检查逐位相同；最终 12 项测试通过，覆盖数值、KV 扩容、分块 mask、真实 prompt、EOS、图生命周期和 CLI 流式显示。

**我额外采用了比项目 A 级更严格的接受标准。** 项目 A 级允许求和顺序变化，要求数学等价；逐位相同和 greedy 序列完全相同是本次实现自己增加的门槛。BF16 输出发生差异，不足以证明拼接 GEMM 或尾部合并在数学上不等价。这些方案被排除，只能说明它们未通过这次更严格的门槛，不能据此断言它们违反 A 级约束。

## 4. 提升是多少？

### 4.1 最终默认配置的配对结果

以下使用**每对加速比的中位数**，定义为 `T_mlx-lm / T_agent`。大于 1 表示更快，小于 1 表示更慢。主实验括号为配对 bootstrap 的 95% 区间；长上下文只有两对，仅列观测范围。区间反映这批重复样本的波动，不能消除热状态、固定单一 prompt 或小样本的局限。

| Prompt 长度 | 对数 | TTFT 加速比 | Decode 加速比 | 可支持的结论 |
| --- | --- | --- | --- | --- |
| 16 | 6 | 1.015 [0.867, 1.269] | 0.997 [0.989, 1.003] | 未证实提升 |
| 64 | 6 | 1.003 [0.941, 1.448] | 1.002 [0.975, 1.007] | 未证实提升，TTFT 波动较大 |
| 512 | 6 | 1.021 [0.973, 1.061] | 0.973 [0.897, 1.018] | TTFT 点估计略好，decode 略差；均未确认稳定效应 |
| 1024 | 6 | 1.002 [0.979, 1.038] | 0.992 [0.976, 1.006] | 未证实提升 |
| 4096 | 6 | 1.003 [0.997, 1.006] | 1.001 [0.998, 1.005] | 基本持平 |
| 16384 | 2 | 0.974 [0.914, 1.034] | 1.029 [1.005, 1.052] | Decode 的有利点估计不足以支持稳定提升 |
| 32768 | 2 | 0.846 [0.835, 0.856] | 0.907 [0.841, 0.973] | 两对均退化，原因未分离 |

**本轮可确认的稳定提升：没有。** 这不是将真实效应估计为严格的 0%，而是现有数据不足以支持一个稳定的正收益结论。

几个绝对数值能说明量级：

- **4k：** TTFT 两侧中位数为 1906.95 → 1901.33 ms；decode 为 17.4715 → 17.4491 ms/token。decode 仅少约 0.0225 ms，约 0.13%，配对区间覆盖 1。
- **16k：** decode 两侧中位数为 33.17 → 32.23 ms/token，延迟降低约 2.81%；但 TTFT 增加约 2.85%，只有两对样本。
- **32k：** TTFT 为 77.24 → 91.37 s，增加约 **18.29%**；decode 为 56.56 → 62.61 ms/token，增加约 **10.71%**。这里的百分比是时间增加比例，不能把 0.846× 加速比直接写成“延迟增加 15.4%”。

### 4.2 为什么不能报告“64-token 提升 25.7%”？

64-token TTFT 两侧中位数是 98.64 → 73.28 ms，看起来延迟降低 25.71%，或者达到 1.346× 加速。但每对实际加速比分别约为：

```text
1.504, 1.395, 0.967, 1.017, 0.915, 0.988
```

只有三对更快、三对更慢，逐对加速比中位数为 1.003×，区间为 [0.941, 1.448]。分别取两侧中位数，丢失了配对关系；在这些波动数据上，它与典型配对效果差异很大。因此，25.71% 只能作为“两侧样本中位数的差异”，不能作为已确认的优化收益。

### 4.3 整个请求是否更快？

同步完最后在途工作后的请求完成时间，两侧中位数在 4k 为 3045.39 → 3041.43 ms，仅下降约 0.13%；32k 为 81.25 → 95.84 s，增加约 17.95%。没有预先规定不同 prompt 长度的业务权重，因此本报告不计算一个任意平均的“总体提升百分比”。

同步 teacher-forced forward 的诊断微基准中，pack-only 配置曾有约 3.2% 的中位数延迟降低。这与端到端异步生成的计时边界不同，不能替代上述最终结果，也不能证明投影融合独立贡献了 3.2%。

## 5. 失败结果带来的修正

第一，**我把较多实现工作投入了本来就接近上界的 decode 固定成本，尚未攻克 prefill 的主要损失。** 保留原 GEMM 和 attention kernel，意味着实际算力效率与长上下文 attention 效率基本沿用了 MLX 后端。新调度器本身无法填满原项目显示的整个 gap。

第二，**严格逐位一致性限制了搜索空间。** Prefill 拼接和 batched GEMM 在 16-token 检查中出现最大 logit 差 0.2734375；尾部合并在 512-token 生成检查失败。后续应区分数学等价、浮点舍入一致和质量一致，依据项目允许的求和顺序变化设计数值容差及质量验证，而不是把任意舍入差都当作算法错误。这样做仍须保留相同权重、BF16 精度和输入，不能借机混入量化收益。

第三，**32k 退化不能全部归咎于热降频。** 热状态是已知混杂因素，但新引擎没有逐块清空 allocator cache，内存布局和缓冲区复用也可能影响长上下文。当前没有缓存池占用、实际 DRAM 流量、GPU 频率或完整 kernel trace，无法判断各因素的贡献。删除无用 graph 引用解决了对象生命周期问题，尚不能据此宣称减少了多少 GPU 复制或延迟。

第四，**少调用与更快之间需要实测证据。** 84 次投影调用的减少是代码结构事实；最终 4k 的约 0.13% decode 延迟下降是测量点估计。两者之间没有经过足够的独立归因实验，不能直接画等号。

## 6. 后续最值得验证的方向

1. **先定位 32k 退化。** 保持其余条件一致，单独消融 allocator 清理策略，记录 active/cache memory、内存压力与 GPU trace；不要先把它解释成热状态问题。
2. **建立持续负载条件下的配对基线。** 记录能够获得的温度/频率信息，等待性能进入相对稳定区间；增加长上下文重复数及多个固定 prompt，报告顺序效应。
3. **优先改 prefill 的有效吞吐。** 对实际小 GEMM 形状做 kernel 或执行计划优化，对长 prompt 的分块 causal attention 做真实调用测量，而不是继续只减少 Python 调度或小算子次数。
4. **分别验证每个优化的贡献。** 用最终生成路径比较 packed projection、residual norm、logprobs 计算和 allocator 策略，避免将多个改动的净结果归给其中一个。

这些是后续实验建议，本次尚未执行；本报告没有把预期收益列入实测提升。

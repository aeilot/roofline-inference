# Qwen3-0.6B 在 MacBook Air M4 上的推理性能上界:结果报告

2026-10-06 · Louis Deng

## 摘要

在 MacBook Air M4 上单流运行 Qwen3-0.6B(BF16),现有引擎的 decode 已达到理论上界的 87–95%,prefill 只有 31–78%。

- **decode 被内存带宽锁死。** 每生成一个 token 都要把 1.19 GB 权重读一遍,上界为 12.2 ms(上下文 512)到 48.2 ms(32k)。mlx-lm 已经很接近,继续优化代码收益很小;要更快,只能改算法(量化、投机解码等)。
- **prefill 被算力锁死,还有 20–70% 的空间。** 短 prompt 的损失在小矩阵乘效率低和每块的固定开销,长 prompt 的损失主要在 attention。(后续实测见"用实现验证上界"一节:短 prompt 的空间已被实际引擎大部分收回;长 prompt 的空间仍在。)
- **热状态的影响和软件低效一样大。** 这台机器没有风扇,同一个 32k prompt 的首 token 时间冷时 55.8 s,连续测试约 40 分钟后 70.7 s,相差 27%。
- **理论部分**:除了标准的上界,本项目自己推导了一个允许融合和重算的 I/O 下界。它在核心级、长 prompt 时比"每个数据只读一次"高约 2 倍,但不改变这台机器上的任何结论。

## 问题与方法

本项目要回答两个问题:在给定设备上,任何实现最快能有多快;现有引擎离这个极限差多少,差在哪里。最终用途是给自动优化推理引擎的 agent 当导航。

**"任何实现"的范围(A 级):** 只改实现,不改数学。每个矩阵乘里的每个乘积项至少算一次;求和顺序、算子融合、重算、softmax 的写法都可以自由选择。量化、投机解码、KV 压缩会改变计算本身,不在这个上界里。

**流程:**

1. 输入模型规格与设备规格;设备参数用自写 Metal kernel 实测校准,每个数都标注来源和置信度。
2. 把一次 decode 或 prefill 写成算子级计算图,得到计算量和必须搬运的字节数。
3. 用 red-blue pebble game 求各级存储边界上的 I/O 下界(多级存储、多核)。
4. 时间下界 = 算力、各级带宽、exp 吞吐这几种资源各自所需时间的最大值。
5. 实测 mlx-lm 与 llama.cpp,用消融实验把它们与上界的差距拆成几部分。

完整推导见 [design-notes.md](design-notes.md)。所有实测都是短时间(burst)数值。

## 理论上界

时间下界 = 几种资源各自"必须干的活 ÷ 每秒能干的活"的最大值。计算和搬运可以同时进行,所以取最大值而不是相加。

```
T ≥ max( W / P,  Q_b / B_b (每条存储边界 b),  N_exp / R_exp )
```

**计算量 W:由模型结构定死。** A 级只允许改实现,每个乘积项都必须算,所以乘法次数是确定的:投影和 MLP 每个 token 对每个权重做一次乘加,attention 每对 (query, key) 做 4 × 128 次运算。

**必须搬的字节 Q:分两层论证。**

1. **必读必写(严格、简单):** 权重和 KV cache 开始时在 DRAM,至少读一次;新的 K/V 和生成的 token 至少写一次;减去开始时可能已在片上的 S 字节。decode 的瓶颈全在这一项。
2. **red-blue pebble game(片上存储有限时更强):** 把执行过程按 I/O 次数切成段,一段能用的数据至多是片上的 S 加段内读入的 R;证明一段至多完成 F 次乘法,而总乘法次数 N 固定,所以 I/O ≥ R × (N / F − 1)。矩阵乘用 Smith 等 2019 的紧常数结果,attention 用 Saha & Ye 2024(常数由本项目从证明中补出)。

**多级存储与多核:** 某一级边界上的流量,把这一级以内的所有存储合起来当作片上容量来算(Savage 1995);多核时每个核单独分段,再把各核的下界相加。本报告用两级:DRAM ↔ 芯片(片上合计 17 MiB),L2 ↔ 核心(每核 512 KiB,10 核)。

**融合 + 重算的下界(本项目新推导):** 融合后,中间结果可以在片上算完直接用掉,也可以重算,现成定理都不覆盖。推导的关键:从头重算一个中间值,必须先把上游一整列权重(2048–5120 个)搬进片上,核心级的小存储付不起。结果:核心级、prompt 32k 时,任何实现至少搬 9.74 GB,是必读必写(4.95 GB)的约 2 倍;prompt 少于约 8k 或在 DRAM 级时不起作用。真实的最小流量落在这个下界和逐算子执行的 135 GB 之间。

| 部分 | 可靠程度 |
| --- | --- |
| 取最大值的形式、W 的计数、必读必写 | 严格,标准论证 |
| 分段论证、矩阵乘的 Smith 界 | 已发表定理,核对过原文;实际分块方案只比它多 5% |
| attention 的常数、推广到 causal 与 GQA | 论文定理加本项目补充的推导 |
| 逐算子的求和规则、融合 + 重算的下界 | 本项目自己的推导,有测试检查,未经同行评审 |
| 峰值算力 P 与带宽 B | 实测最好值,不是硬件绝对极限;硬件若能更快,上界可能被略微超过 |

exp 是 softmax 里的指数函数,每个 attention 分数算一次,单列为一种资源;在 M4 上它只占计算时间的约 1.6%,不会成为瓶颈。

## 硬件实测

喂饱算力需要的并发比喂饱带宽多一个数量级:带宽约 1k 个线程就跑满,算力要约 32k 个。下表是方案代价模型用到的其余校准量(全部用自写 Metal kernel 测量)。

| 量 | 结果 | 含义 |
| --- | --- | --- |
| 每个有依赖的 kernel 的 GPU 固定成本 | 2.44 µs | barrier、启动、爬坡 |
| 依赖 kernel 链的稳态读带宽 | 93.9 GB/s | 低于单个大 kernel 的 102.7 |
| 每个 kernel 的 CPU 编码 / 每个 command buffer 提交 | 2.46 µs / 17.4 µs | 多个 buffer 时与 GPU 执行重叠 |
| GPU → CPU 同步 | 148 µs | 每 token 同步一次就要付,流水线可以藏住 |
| prefill 矩阵乘(mx.matmul,Qwen3 形状) | M ≥ 512:3.15–3.26 TFLOP/s;M = 16:0.6–1.2 | 小矩阵乘给不出足够并行 |
| prefill attention(2048 行一块) | 2.8 TFLOP/s | 峰值的 76% |
| exp 吞吐 | 0.46 万亿次/秒 | softmax 的资源 |
| 跑满 DRAM 所需在途数据 | 约 29 KiB(约 1.8k 个 16 B 请求) | Little 定律,延迟 290 ns |
| 带宽 / 算力到 90% 所需并发线程 | 1024 / 32768 | 算力比带宽难喂得多 |

依赖 kernel 链的模型必须把 CPU 编码单列:只有一个 command buffer 时,GPU 要等 CPU 编码完才开始。拆开后,预测误差的中位数是 3.5–5.5%。

## 基线:现有引擎离上界多远

## 差距分解:mlx-lm 的时间花在哪里

![mlx-lm 实测时间中物理上界与各段损失的占比](../results/figures/gap_mlx.png)

*mlx-lm 消融实验 · 2026-10-06,连续测试后(较热),各变体交错 3 轮取最小(L > 4k 为 1 轮)*

孤立测量的 kernel 时间不能直接相加(decode 的 GEMV 单独测时互相抢带宽,加起来比整步还慢),所以用消融实测:只留矩阵乘 → 加 attention → 完整 forward → mlx-lm 的 generate,每一段减去它在物理上界中的理想份额,就是该段的损失。

- **decode:** 只损失 7–16%;调度开销约为 0,mlx-lm 的异步流水线把每 token 的 CPU 工作(建图 0.53 ms、编码约 1.3 ms)和同步都藏在 GPU 时间后面;536 个小 kernel 的固定成本大多与带宽型工作重叠。
- **用校准参数预测的方案时间:** decode 高估 0.3–11%(孤立代价假设没有重叠);prefill 在 64–4k 范围内误差 7% 以内,16k–32k 低估 16–24%。
- **热状态:** 这组数据是在连续测试后测的,32k 的首 token 时间为 70.7 s,而上一节较冷时为 55.8 s;长 prompt 的 attention 损失里有一部分是降频,尚未分开。

## 性能随快存储容量与并行度的变化

传统 roofline 把算术强度(AI)当作输入;这里 AI 是从计算图和快存储容量 S 推出来的:AI 上限 = 计算量 ÷ 最小必须搬运量。结论:单流 decode 的 AI 约为 1.3,任何不到约 1 GB 的片上存储都改变不了;prefill 在 S 超过约 5–10 KiB 后就是算力瓶颈。

![性能上界随快存储容量 S 的变化](../results/figures/perf_vs_capacity.png)

- 实线是对任何实现都成立的下界(含本项目的融合 + 重算界),虚线是逐算子执行的下界。小 S 时实线也大致按 √S 上升:prefill 4k 在 S = 32 KiB 时 AI 上限为 723(逐算子 95)。
- S 大到能放下全部权重和 KV 时,稳态不再有 DRAM 流量,AI 没有上限。

第二个维度是并发度:要跑满带宽和算力,实现必须同时保持足够多的线程。下图左、中为 decode 4k 与 prefill 4k 在 (S, 并发线程数) 上的上界,各自按最好情况归一化;右为实测的带宽与算力随并发的变化。

![性能上界随容量与并行度的变化](../results/figures/perf_capacity_parallelism.png)

- decode 只要约 1k 个并发线程(约 29 KiB 在途数据)就到最好上界的 90%,与 S 基本无关。
- prefill 到 90% 需要 16k–32k 个并发线程;短 prompt 的小矩阵乘效率低,根源是给不出这么多并行,而不是带宽不够。

## 用实现验证上界(agent-test/v2)

上界是下界,单独看不出它有多紧。为此实现了一个仍在 A 级内的引擎(BF16 权重与 KV,只改实现),与 mlx-lm 的 `generate_step` 做热状态门控的配对对照。细节、数据与局限见 [agent-test/v2/README.md](../agent-test/v2/README.md)。

- **decode 的上界基本是紧的。** v2 达到上界的 95.7–99.3%(mlx-lm 为 92–93%),相对于校准带宽 102.7 GB/s 而言,A 级剩余空间约 1–4%。这印证了"decode 被带宽锁死"。
- **短 prompt 的诊断得到证实。** 按"小矩阵乘效率低 + 每块固定开销"修改后,TTFT 在 16 / 64 / 256 个 token 时分别快 1.72 / 1.56 / 1.26 倍。
- **长 prompt 的损失在 attention 的数据路径和降频,不在 softmax。** 在同一个 attention kernel 上去掉 softmax 或 exp,吞吐都不升高;kernel 约为实测 MMA 峰值的 77–80%。持续 60 s 时纯 MMA 不降速,attention 降 12%。因此上界的资源项不需要修改,但长 prompt 的空间需要更好的 attention kernel 才能收回;v2 在 4k–32k 只快 4–8%。
- **未验证:** 上界作为导航是否比单纯剖析更有用。对照实验设计见 [navigation-experiment.md](navigation-experiment.md)。

## 局限与下一步

最大的未知是热状态:所有数字都是短时间测量,而无风扇的机器连续负载后会降频。

- **持续负载(优先):** 在降频后的稳定状态重测带宽、算力和基线,并把长 prompt 的 attention 损失与降频分开。
- **收紧融合下界:** 现在和逐算子执行之间还差约 14 倍;可以按算子分别分配预算、计入 attention 与 o_proj、把重算的前置条件往上游推得更深。
- **prefill 每块开销:** 短 prompt 时模型低估了小 kernel 与调度开销(每块两次求值、清空分配器缓存)。
- **计算图侧的并行度:** 目前的并行度是"实现保持了多少并发",还没有计入依赖链与算子宽度对并发的限制。
- **llama.cpp:** 只有总时间,没有拆开;decode 32k 未测;32k prefill 的断崖原因未查。
- **给 agent 的接口:** 结果目前在图与笔记里,还没有"给定一个方案,返回预计时间与瓶颈"的可调用接口。
- **后续阶段:** 量化(B 级)、投机解码与 KV 压缩(C 级)、batching、多引擎(CPU / GPU / ANE)分配。

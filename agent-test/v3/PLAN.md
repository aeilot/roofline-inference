# 验证方案 v3：v2 引擎是否真的快于 mlx-lm

2026-10-06 · 状态：已实现（见 [README.md](README.md)），尚未正式采集

## 0. 为什么需要 v3

v2 的对照（[../v2/README.md](../v2/README.md)）有以下缺陷，结论尚不能算证实：

| # | v2 的缺陷 | 后果 |
|---|---|---|
| D1 | 两个引擎在同一进程中交替运行，共享 MLX 缓冲区缓存、编译缓存和 GPU 状态；运行前不清缓存，mlx-lm 会自己清，v2 不清 | 可能互相影响；先后顺序检验显示短 prompt TTFT 有 −16% 到 +30% 的顺序效应，无法与噪声区分 |
| D2 | `mx.synchronize()` 只同步默认 stream，没有同步 mlx-lm 的 `generation_stream` 和 v2 自己的 stream | 前一次运行的在途工作只靠门控时的空等保证结束；"整个请求"时间少算了最后一个在途 token |
| D3 | 每个长度的 6 对连续测完，再测下一个长度 | 时间漂移与长度混在一起 |
| D4 | 样本量没有事先计算；短 prompt TTFT 的对数比值标准差为 0.07–0.27，6 对远远不够 | 短 prompt 的区间不可信 |
| D5 | 加速比混合了 kernel 改进和调度差异（mlx-lm 的 `clear_cache`、concat 扩容、logprobs、L−1+1 分块） | 无法说明快在哪里 |
| D6 | 只用随机 token prompt 计时 | 外推到真实负载缺少依据 |
| D7 | 开发者自己设计、测量、解读，分析方式在看到数据后才确定 | 存在研究者自由度 |
| D8 | 只做了一次，所有测量在同一个下午 | 无法排除当天机器状态的影响 |

v3 针对每一条给出对策（括号中注明对应的缺陷编号）。

## 1. 要检验的假设（事先登记）

- **H-dec**：在每个上下文长度下，v2 的 decode 每 token 时间短于 mlx-lm。
- **H-ttft**：在每个 prompt 长度下，v2 的 TTFT 短于 mlx-lm。
- **H-req**：在固定请求组合下，v2 的整个请求时间（包括最后的在途工作）短于 mlx-lm。

**"证实更快"的判据：** 几何平均比值（mlx-lm 耗时 ÷ v2 耗时）的 95% 区间下限 **> 1.02**。2% 是实际意义阈值，区间刚好越过 1 不算。区间完全落在 [0.98, 1.02] 内判为"等价"，其余情况判为"未定"。

**最小样本量：** 一个场景总共少于 6 对、或任一时段少于 3 对时，判为"样本不足"，不下结论（冒烟测试表明，样本量为 1 时 bootstrap 区间会退化为一个点，给出虚假的确定性）。

多重比较：按场景族（decode、TTFT、请求）分别做 Holm 校正。

## 2. 被测对象

| 编号 | 引擎 | 用途 |
|---|---|---|
| **E0** | mlx-lm `generate_step`，默认配置 | 主基线，也就是用户直接用 mlx-lm 时的情况 |
| **E1** | mlx-lm 的模型 forward + 公平调度：整段 prefill、只对最后一行算 logits、不清缓存、预分配 KV、不算 logprobs | 把调度差异和 kernel 改进分开（D5） |
| **E2** | v2 完整版，冻结在提交 `228fa5b` | 被检验对象 |
| **E2-x** | v2 关闭单项优化：x ∈ {skinny GEMM, 融合 GEMV, GQA attention, prefill 融合} | 逐项消融，属于次要分析 |

E0→E1 的差距是调度带来的，E1→E2 的差距是 kernel 带来的。主结论只用 E0 对 E2；E1 和 E2-x 属于解释性分析，不参与"证实更快"的判定。

E1 与 E2-x 的实现需要先通过 `check.py`，然后冻结。

## 3. 隔离（D1、D2）

- **每次计时一个新进程。** 一个 worker 进程只加载一个引擎，按以下顺序执行：
  1. 加载模型；
  2. 用同形状、不同内容的 prompt 跑一次预热请求；
  3. 门控（见第 4 节）；
  4. 跑一次计时请求；
  5. 写出结果后退出。
  进程之间不共享任何 MLX 状态。
- **同步。** 由每个引擎暴露自己的 stream，计时结束时调用 `mx.synchronize(engine_stream)`，并检查之后该 stream 上没有在途工作。"整个请求"时间以这个同步点为准。
- **调度器**是一个独立的父进程，只负责排序、门控、启动 worker 和收集结果，自身不加载 MLX 模型。
- **残留影响检验。** 增加专门的"延续性"块：在同一时段内按 A→B 与 B→B 的顺序各跑多次，比较 B 的耗时。如果差异的区间包含 0 且小于 2%，则认为进程隔离后不存在可测的延续影响；否则报告延续效应的大小。

## 4. GPU 状态与热控制

每次计时前，调度器依次：

1. 等 `thermalState == 0`，且固定探针（约 10 ms 的矩阵乘）不慢于当时段基准的 10%（初稿为 5%：刚加载完模型的 worker 中探针本身就高 3–4%，导致每次多等约 1 分钟；探针对持续降频不敏感，主要依据是 thermalState）。超过 10 min 仍未满足，就记录为"超时"并跳过这一次（计入报告）；
2. 按状态组准备 GPU：
   - **idle**：空等 2 s，模拟新到的用户请求；
   - **warm**：跑 150 ms 固定负载；
   - **sustained**：不门控，同一引擎连续跑 N 个请求，只取第 2 个以后的，用来看持续负载。

主分析使用 **idle**，因为它最接近真实单次请求；warm 和 sustained 作为补充。每次计时都记录前后的热状态、探针读数、系统负载以及当时运行的其他进程数。

## 5. 场景与工作负载（D6）

| 族 | 场景 |
|---|---|
| TTFT | prompt 16、64、256、1024、4096、16384、32768 |
| decode | 上下文 512、4096、16384、32768，生成 129 个 token，去掉前 2 个间隔后取中位数 |
| 整个请求 | (prompt 256, 生成 256)、(1024, 512)、(4096, 128) |

- **Prompt 来源。** 一半是随机 token（固定 seed），另一半是真实文本：从仓库内固定文件截取（中文报告、英文 README、Python 源码），按 tokenizer 截到目标长度，并记录 SHA256。
- **长度交错（D3）。** 所有场景、引擎和 prompt 类型组成一个完整列表，按区组随机化排序：每个区组覆盖每个场景各一次，区组内顺序随机，随机种子事先写入方案。这样时间漂移不会和某个长度混在一起。

## 6. 样本量（D4）

根据 v2 估计的对数比值标准差，目标是 95% 区间的半宽约 ±2–5%：

| 场景 | 估计标准差 | 每种状态的配对数 |
|---|---|---|
| decode（全部） | ≤ 0.014 | 12 |
| TTFT ≥ 1024 | ≤ 0.017 | 12 |
| TTFT 256 | 0.024–0.27 | 30 |
| TTFT 16、64 | 0.07–0.20 | 40（半宽约 ±6%） |
| 16k、32k | 未知 | 6（每个 32k 请求约 60 s，成本最高） |
| 整个请求 | 未知 | 12 |

**预计机器时间：** idle 状态的主实验约 6–8 h（每次计时都要启动进程、加载模型、门控），warm 状态约 4 h，消融约 4 h。可以分多个时段执行，见第 8 节。

## 7. 分析（D7）

分析脚本 `analyze.py` 在采集数据**之前**写好并提交，看到数据后不再修改：

- 主统计量：配对对数比值的均值，按区组做 bootstrap（10 000 次）求 95% 区间，再指数化为几何平均比值。
- 每个场景同时报告：中位数比值，两个引擎各自的绝对耗时中位数和四分位距。
- **排除规则只有两条**，都在事先固定：
  1. 门控超时；
  2. worker 崩溃。
  被排除的记录全部保留在原始数据中，并在报告中计数。
- 正确性门槛（`gate.py`，每个时段开始时运行一次，约 1500 个位置。初稿只有 624 个位置，p99 统计量只取决于第 8 大的值，E1——本质上就是 mlx-lm 自己的数学——仅因噪声就超标 3%。这一调整在采集正式数据前完成）：冻结的代码先运行 `check.py`（FP32 容差标准）和 `test_engine.py`。每次计时都记录生成序列；序列分叉一律用 FP32 前向判断是否为近似平局，结果写入报告。不是近似平局的分叉，会让该场景的结论作废。
- 延续性检验与消融结果单独报告，不参与主判定。

## 8. 复现（D8）

- **两个时段。** 主实验分在两天执行，各占一半区组。以时段为分层做 bootstrap，并分别报告每个时段的结果。如果两个时段的结论方向不一致，判为"未定"。
- **独立执行。** 由开发者以外的人（用户本人）在自己的终端用一条命令运行完整流程：

  ```sh
  .venv/bin/python agent-test/v3/run.py --session 1
  ```

  分析由同一个冻结的脚本完成。开发者不手动筛选数据。
- 每份原始结果都记录：被测提交的 SHA、各被测文件的 SHA256、MLX 和 mlx-lm 的版本、macOS 版本、开始和结束时间。

## 9. 需要实现的内容

| 文件 | 内容 |
|---|---|
| `adapters.py` | E0、E1、E2、E2-x 的统一接口：`load()`、`generate(prompt, n)`、`stream()` |
| `worker.py` | 单次计时的子进程：加载 → 预热 → 等调度器信号 → 计时 → 同步 → 写出 JSON |
| `run.py` | 调度器：生成随机化区组、门控、启动 worker、记录状态、支持中断后续跑 |
| `prompts.py` | 固定的随机 token 与真实文本 prompt，并记录 SHA256 |
| `analyze.py` | 事先冻结的分析与报告生成 |
| `carryover.py` | 延续性检验块 |
| `e1_fair_baseline.py` | E1：mlx-lm 模型 forward 加上公平调度 |

实现顺序：先写 adapters、worker、run、prompts、analyze，并跑一个约 15 min 的冒烟测试（每个场景 2 对），检查流程能完整跑通。冒烟数据**不进入**正式分析。然后冻结代码，记录提交 SHA，再开始正式采集。

## 10. v3 的结论如何改写 v2 的报告

- 被 v3 证实的场景，v2 README 中对应的表述保留，并改为引用 v3 的数字。
- 判为"未定"或"等价"的场景，从"更快"中删除，并说明原因。
- 如果 E1 与 E2 差距很小，那么 v2 的收益主要来自调度而不是 kernel，第 4 节的归因要相应改写。

在 v3 完成之前，v2 README 中短 prompt 的 TTFT 结论视为**未证实**。

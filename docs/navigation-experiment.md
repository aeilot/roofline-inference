# 对照实验设计：上界作为导航，是否比单纯剖析更有用

2026-10-06 · 状态：设计稿；预实验（P、B 两组各 2 次）已于 2026-10-08/09 完成，见 [PILOT.md](../agent-test/nav/PILOT.md) 与 [report.md](report.md)；正式实验尚未执行

## 1. 要回答的问题

本项目的最终用途是给优化推理引擎的 agent 当导航（见 [report.md](report.md)）。agent-test/v2 说明，一个看过上界的 agent 能做出比 mlx-lm 更快的引擎，但没有说明**上界本身起了多大作用**：同样的改进也可能只靠逐段剖析就能找到。

**主假设 H1：** 在相同预算下，拿到上界与差距分解的 agent，做出的引擎更快。

**次假设：**
- **H2：** 上界组把更少的预算花在"上界已显示几乎没有空间"的方向上。
- **H3：** 上界组对"还剩多少空间、何时该停"的判断更准确。

## 2. 实验组

各组只在**提供的材料**上不同，其余全部相同：同一个模型和提示模板，同一个起点代码，同样的工具、预算和正确性门槛。

| 组 | 提供的材料 | 作用 |
|---|---|---|
| **P 剖析组** | 起点代码、mlx-lm 基线、计时与逐段消融脚本、正确性检查器、硬件校准表（带宽、算力等实测数，**不含**上界与差距分解） | 对照 |
| **B 上界组** | P 的全部材料，加上各场景的上界 T_bound、差距分解图表，以及"放宽约束 X 会怎样"的问答接口 | 处理 |
| **N 信息量对照组** | P 的全部材料，加上与 B 篇幅相当、但不含上界的中性材料（例如 Metal 编程指南摘录） | 排除"多给了上下文"本身的效果 |
| **W 错误上界组**（可选） | 与 B 相同，但 decode 上界被人为调低 30%，长 prompt prefill 上界被调高 30% | 操纵检验：agent 是否真的按上界做决策 |

W 组的预期：如果 agent 真的依据上界决策，W 组会在 decode 上投入更多预算（以为还有空间），并更早放弃长 prompt。如果 W 与 B 的行为没有差别，说明上界没有被实际使用，那么 H1 即使成立，机制也不是导航。

## 3. 隔离与起点

- **起点**：第一轮引擎 `agent-test/benchmarked-engine.py`（A 级、未用上界调优）。不能用 v2，因为 v2 本身就是在上界指导下做出来的。
- **隔离**：每次运行使用独立的仓库副本，只包含该组允许的材料。去掉 `docs/`、`results/` 和 `agent-test/v2`，P 组还要去掉 `src/` 里计算上界的代码。
- **约束**：A 级（BF16 权重与 KV、只改实现）；正确性统一用 `agent-test/v2/check.py` 的 FP32 容差标准，agent 可以随时调用，最终由评估者重跑。
- **残余污染**：模型本身对 Apple GPU 和 roofline 的先验知识无法去除，各组相同，接受这一点并在报告中写明。

## 4. 预算

每次运行的预算相同，在提示中明确给出，由运行框架强制执行：

- 固定的 agent token 预算（例如 4M）和挂钟时间（例如 3 h）；
- 固定次数的正式计时调用（例如 40 次）。agent 自己的小规模剖析不计入次数，但计入时间。

**计时必须串行。** 只有一台 M4，GPU 计时互相干扰，热状态也会串扰。各组的开发可以并行，但所有计时请求进入同一个带锁的队列，并经过 `thermalState` 门控。队列等待时间不计入 agent 的挂钟预算。

## 5. 度量（预先注册）

**主指标：最终引擎相对 mlx-lm 的几何平均加速比。**

- 场景集固定：decode（上下文 512 / 4k / 32k）和 TTFT（prompt 16 / 256 / 4k / 32k），共 7 个场景，等权。
- 由**独立评估者**在全部运行结束后统一测量，不采用 agent 自报的数字；使用 `agent-test/v2/benchmark.py` 的热态门控协议，每个场景 6 对（32k 为 3 对）。
- 未通过正确性检查的引擎，主指标记为 1.0（等于 mlx-lm）。

**次指标：**

1. **无效投入比例（H2）**：花在"预计可得收益 < 3%"方向上的预算占比。按事先写好的编码规则，从 transcript 中把每段工作归类到 decode GEMV、decode attention、prefill GEMM、prefill attention、调度、其他；"预计可得收益"由各方向的上界空间事后计算，各组用同一标准。
2. **剩余空间判断（H3）**：要求 agent 在结束时对每个场景写出"还能再快多少"，再和事后测得的空间比较，计算绝对误差。
3. 首次达到 1.05 倍主指标所用的预算。
4. 无效宣称数：agent 报告了、但评估者复测不成立的加速，或不满足统计要求的宣称。

## 6. 样本量与分析

- **先做预实验**：每组 2 次运行，用来估计运行间方差并检查运行框架。
- **正式实验**：初定每组 8 次（P、B、N 共 24 次，W 另加 4 次）。根据预实验的方差重新计算：如果要以 80% 功效检测主指标 0.05 的差异，所需次数可能明显多于 8。
- **主检验**：B 对 P、B 对 N 的主指标差，用 bootstrap 95% 区间加 Mann-Whitney U，Holm 校正多重比较。只有 B 同时优于 P 和 N，才算支持 H1。
- **次指标**只做描述性报告，不作为确证性结论。

## 7. 盲法

- 评估者只拿到引擎代码和运行编号，不知道组别。
- transcript 编码者无法完全盲化，因为 B 组的 transcript 会提到上界。缓解办法：编码前用脚本把"上界""bound""roofline"等词替换为中性占位符，并由两名编码者独立编码，报告一致性（Cohen's κ）。

## 8. 威胁与对策

| 威胁 | 对策 |
|---|---|
| 热状态与机器漂移 | 计时串行加门控；最终评估集中在一个时段内，组别交错排序 |
| agent 随机性很大 | 足够的运行次数；固定模型版本和采样设置 |
| B 组只是因为上下文更多 | N 组 |
| B 组提升了，但不是因为导航 | W 组的操纵检验，以及次指标 H2/H3 的机制证据 |
| 起点太差，任何组都能轻易提升 | 同时报告相对起点和相对 mlx-lm 的加速比 |
| 场景权重是人为选定的 | 同时报告每个场景的单独结果 |

## 9. 需要先实现的部分

1. 材料包生成脚本：按组生成隔离的仓库副本。
2. 统一的提示模板和预算执行器（token、时间、计时调用次数）。
3. 带锁的计时队列服务（复用 `agent-test/v2/thermal.py` 和 `benchmark.py`）。
4. 评估者脚本：给定引擎目录，输出主指标和正确性结果。
5. transcript 编码手册和占位符替换脚本。
6. 上界问答接口：给定"放宽约束 X"，返回新的 T_bound。这是 B/W 组的材料，目前只有图表和笔记形式，需要做成可调用接口（见 report.md 的"给 agent 的接口"）。

## 10. 成本估计

每次运行约 3 h 开发，加上队列中约 40 次计时（每次 1–3 min）。正式实验 28 次运行，仅计时就约需 40–80 h 的独占机器时间，最终评估另需约 10 h。预实验 8 次大约 1–2 天。
